# PAM Player Manual (`pam_player.py`)

## Purpose

`pam_player.py` is the Manim scene runner for PAM JSON screenplays. It reads a JSON array of action objects, builds characters and props, plays the scene sequentially, and optionally drives camera motion from Fountain-generated prompt metadata.

The key architectural point is this:

**`pam_player.py` does not define its own argparse-style command-line flags.**
You run it through **Manim’s CLI**, and you control PAM-specific behavior mainly with **environment variables**.

This manual describes the player as of PAM 1.0.1, including the frame clock, sequences, timed parallel blocks, contact constraints and choreography routines added for the Blender roadmap (section 9). Module docstrings in `pam/timeline.py`, `pam/constraints.py` and `pam/choreography.py` hold the design notes; the README has worked examples.

---

## 1. How to run it

### Direct Manim invocation

```bash
manim -pql pam_player.py PAMPlayer
```

This renders the `PAMPlayer` scene class from `pam_player.py`.

### Use a specific screenplay JSON

```bash
PAM_SCRIPT=my_scene.json manim -pql pam_player.py PAMPlayer
```

### Show the render-time clock

```bash
PAM_SCRIPT=my_scene.json PAM_SHOW_CLOCK=1 manim -pql pam_player.py PAMPlayer
```

### Disable camera mode

```bash
PAM_CAMERA_MODE= PAM_SCRIPT=my_scene.json manim -pql pam_player.py PAMPlayer
```

Set the variable to nothing, as shown. `PAM_CAMERA_MODE=0` leaves camera mode on (see section 3).

### Supply an explicit prompts JSON for camera-mode

```bash
PAM_CAMERA_MODE=1 PAM_SCRIPT=my_scene.json PAM_PROMPTS=my_scene_prompts.json manim -pql pam_player.py PAMPlayer
```

## 2. What is the actual CLI surface?

There are **two layers** of runtime control.

### Layer A: Manim CLI arguments

These are not defined by PAM; they come from Manim.

Typical pattern:

```bash
manim [MANIM OPTIONS] pam_player.py PAMPlayer
```

Common examples:

- `-p` — preview after render
- `-ql` — low quality
- `-qm` — medium quality
- `-qh` — high quality
- `-qk` — 4K

So in practice, the true operator-facing command is a combination of:

1. **Manim flags**
2. **PAM environment variables**
3. the script file `pam_player.py`
4. the scene name `PAMPlayer`

### Layer B: PAM-specific environment variables

These are the real `pam_player.py` runtime parameters.

---

## 3. PAM-specific runtime parameters

## `PAM_SCRIPT`

**Purpose:** path to the PAM JSON screenplay file.

**Default:**

```text
screenplay.json
```

**Example:**

```bash
PAM_SCRIPT=episode_01.json manim -pql pam_player.py PAMPlayer
```

**What it affects:**
- which JSON file is loaded into `actions`
- all scene content, cast, props, dialogue, camera markers, captions, and timing

**Failure mode:** if the file does not exist or is invalid JSON, the render will fail when `pam_player.py` tries to open or parse it.

---

## `PAM_CAMERA_MODE`

**Purpose:** enable or disable automatic camera behavior.

**Default behavior in code:** effectively **on by default**.

The player uses:

```python
bool(os.environ.get("PAM_CAMERA_MODE", "1"))
```

So if the variable is absent, camera mode is treated as enabled.

### Important caveat
Because the code uses Python `bool()` on the environment string, **any non-empty string is truthy**. That means:

- `PAM_CAMERA_MODE=1` → on
- `PAM_CAMERA_MODE=true` → on
- `PAM_CAMERA_MODE=0` → **also on**, because the string `"0"` is truthy
- `PAM_CAMERA_MODE=` (set to nothing) → off

The documentation intends `0` to mean off, but the implementation uses `bool(string)` rather than a strict parser. If you want this behavior to be completely robust, the code would ideally parse values explicitly.

### Operational intent
When enabled, the player:

- loads prompt metadata from `PAM_PROMPTS` or the auto-derived prompts path
- watches `_subscene_marker` entries in the PAM JSON
- applies or queues camera moves based on `shot_meta`

### When disabled
The scene still renders, but the automatic camera system is bypassed.

---

## `PAM_PROMPTS`

**Purpose:** path to the prompts JSON file generated by `fountain2pam.py`.

**Used only when camera mode is active.**

**Default:** auto-derived from `PAM_SCRIPT` by replacing `.json` with `_prompts.json`.

Example:

- `PAM_SCRIPT=scene.json`
- default prompts path becomes `scene_prompts.json`

**Example explicit use:**

```bash
PAM_CAMERA_MODE=1 PAM_SCRIPT=scene.json PAM_PROMPTS=scene_prompts.json manim -pql pam_player.py PAMPlayer
```

**If the prompts file is missing:**
- the player prints a message
- camera mode remains on
- it falls back to inline `_shot_meta` stored directly on `_subscene_marker` actions

This fallback is useful when the screenplay JSON already embeds camera metadata.

---

## `PAM_SHOW_CLOCK`

**Purpose:** show a live render-time clock in the upper-right area of the frame.

**Default:** off.

**Effect:** displays elapsed render time in `M:SS.ss` format.

**Recommended use:** low-quality preview renders only.

**Example:**

```bash
PAM_SCRIPT=scene.json PAM_SHOW_CLOCK=1 manim -pql pam_player.py PAMPlayer
```

**What it does not affect:**
- scene timing logic
- animation behavior
- JSON parsing
- output semantics

It is strictly an on-screen diagnostic overlay.

## 5. Relationship to `pam-render`

The README also mentions a shell wrapper named `pam-render`.

That wrapper is the place where you get a more traditional flag-based CLI such as:

```bash
./pam-render --script screenplay.json --output my_animation --quality l
```

and optionally:

```bash
./pam-render --script screenplay.json --show-clock
```

So:

- **`pam_player.py` itself** = Manim scene + environment variables
- **`pam-render`** = convenience wrapper with operator-friendly flags

If you are documenting “CLI arguments,” distinguish these two clearly.

## 6. What `construct()` does at runtime

Inside `PAMPlayer.construct()`, the sequence is roughly:

1. Set the background color.
2. Read `PAM_SCRIPT` and load the JSON action list.
3. If camera mode is on, load prompts JSON and build a `subscene_id -> shot_meta` lookup.
4. Consume and render an initial `title` action if present.
5. Consume and render one `persistent_caption` action if present.
6. Enable the optional clock if `PAM_SHOW_CLOCK` is set.
7. Initialize registries for cast, props, scene objects, and zones.
8. Reset the camera to a wide shot at scene start when camera mode is active.
9. Iterate through the remaining JSON actions in order.
10. Clean up persistent caption, title, subtitle, and clock at the end.

This is useful to know because some actions are treated specially before the main loop.

## 7. Screenplay structure

The screenplay file is a **JSON array of action objects**.

Example skeleton:

```json
[
  {"action": "title", "text": "Scene 1", "subtitle": "Lobby"},
  {"action": "cast", "characters": {
    "alice": {"build": "narrow", "offset": [-3, 0, 0]}
  }},
  {"action": "fade_in", "who": "alice"},
  {"action": "say", "who": "alice", "text": "Hello."},
  {"action": "fade_out", "who": "alice"}
]
```

Objects containing only `_comment` or `_hint` are skipped.

## 8. Special top-level actions handled directly by `pam_player.py`

These actions are not merely delegated; the player itself owns their logic.

## `title`

Used only if it is the **first action** in the screenplay.

### Keys
- `text` — main title text
- `subtitle` — optional subtitle line
- `y_offset` — top-edge buffer used when placing the title

### Example

```json
{"action": "title", "text": "Act I", "subtitle": "Observatory"}
```

---

## `persistent_caption`

A static caption bar that remains visible for the full scene.

### Keys
- `text` — required caption text
- `position` — `bottom`, `lower-third`, or `top`
- `style` — `normal`, `italic`, or `bold`
- `font_size` — integer, default 16

### Notes
- only the first such action is consumed at startup
- it is removed from the normal action stream
- it does not block the rest of the scene

---

## `_subscene_marker`

A synchronization marker used by camera mode.

### Keys
- `_subscene_marker` — subscene id string
- `_shot_meta` — optional inline shot metadata
- `bg_color` — optional background color override
- `zone` — optional spatial zone name
- `at`, `frames` — only inside a timed `parallel` block (section 9): the frame the camera cuts on, and, for a move, how many frames it takes

### What it does
Depending on the `move` field in shot metadata, the player may:

- apply an immediate static cut
- defer a camera move until the next bubble appears
- execute `pan-up`
- execute `pan-down`
- execute `descend`
- execute `push-into`

This is the core of automatic camera sync.

---

## `cast`

Declares cast members before they are faded in.

### Required shape

```json
{
  "action": "cast",
  "characters": {
    "alice": {...},
    "bob": {...}
  }
}
```

### Character keys
- `figure_type` — `human`, `alien`, `dog`, or `dodecahedron`
- `pose` — initial pose name
- `offset` — `[x, y, z]`
- `style` — style dict
- `build` — body build, usually `default`, `narrow`, `broad`, `alien`
- `scale` — dict with `sx`, `sy`, `anchor`
- `color` — color hex
- `torso_color` — second color for torso zone
- `gender` — figure-dependent preset
- `spawn` — spawn metadata for prop-characters

### Important note
`cast` registers characters, but does **not** draw them. Rendering happens on later `fade_in` actions.

---

## `fade_in`

Creates the figure if needed and animates it into the scene.

### Keys
- `who` — character key
- `pose` — optional override of starting pose
- `offset` — optional override of position
- `style` — style dict
- `build` — build override
- `figure_type` — `human`, `alien`, or `dog`
- `scale` — optional scaling spec
- `gender` — optional gender preset
- `torso_color` — optional torso color override
- `duration` or `rt` — fade timing

### Notes
- if a `cast` block exists, `fade_in` can inherit from it
- for dogs, fade timing uses dog-specific fade parameters

---

## `say`

Character speech bubble.

### Keys
- `who` — speaker
- `text` — required dialogue text
- `hold` — bubble hold time, default 1.2
- `rt_in`, `rt_out` — fade-in and fade-out times, defaults 0.4 and 0.3
- `font_size` — default 20
- `side` — bubble side, default `right`
- `style` — `normal`, `os`, or `phone`
- `persist` — keep the bubble until `clear_bubble` / `clear_all_bubbles`
- `duration` — keep the bubble for this many seconds, then let it expire
- `frames`, `frames_in`, `frames_out` — length of the whole line, and of its fades, in frames at 15 per second (section 9)

### Notes
- consumes any deferred camera move so the camera can move together with the bubble fade-in
- `style="os"` uses the off-screen/phone bubble variant
- a `say` with `frames` lasts exactly that many frames, fades included, and can be a step of a timed `parallel` block, where it overlaps other action; a `say` without `frames` plays as it always has

---

## `wave`

Arm-lift plus wag action.

### Keys
- `who` — character name
- `hand` — `right` or `left`
- `cycles` — wag count, default 2
- `rt_lift` — raise/lower time, default 0.4
- `rt_wag` — per-wag keyframe time, default 0.24

---

## `scene_props`

Opening-stage prop declaration. Functionally similar to `props`, but intended for the initial stage layout.

### Keys
- `items` — dict of prop specs
- `rt` — fade-in time for built props

### Per-item prop keys
At minimum, each item usually includes:
- `type`
- `x`
- optionally `y`, `color`, `label`, `height`, `parent`, `attach`, `attrs`, `hidden`

### Notes
- child props are built after parents
- hidden props are registered but not shown until later

## `scene_objects`

Background dressing that the camera can target without treating them as interactive props.

### Keys
- `items` — dict of scene object specs
- `rt` — fade-in time

### Typical per-item fields
- `type`
- `x`
- `y`
- `color`
- `label`
- `height`

### Notes
- stored separately from interactive props
- usable as camera `SUBJECT` values
- backdrops are pushed behind everything else

### Keys

### Per-zone keys

## `sound_cue`

Short diegetic label such as `RING!` or `KNOCK!`.

### Keys
- `label`
- `display` — bool, default true
- `hold` — default 0.6
- `rt_in` — default 0.15
- `rt_out` — default 0.20
- `x` — horizontal offset
- `y` — vertical offset
- `font_size` — default 22 (Milestone 6)
- `color` — default `"#ffdd55"` (Milestone 6)

### On the frame clock (Milestone 6)
With `frames`, `frames_in` or `frames_out`, or as a step of a timed
`parallel` block (with `at`), the word fades in, holds and fades out on
exact frames, while other steps play: `frames` is the whole,
`frames_in` and `frames_out` the fades (defaults 2 and 3 frames, from
`rt_in` and `rt_out`; the hold defaults to 9). Without those keys it
plays as before, by itself.

```json
{"action": "sound_cue", "label": "THUD!", "font_size": 44, "x": 0.4,
 "y": -0.6, "frames": 15, "frames_in": 1, "frames_out": 3, "at": 6}
```

### Keys

## `parallel`

Play multiple actions at once.

### Keys
- `do` — list of sub-actions
- `rt` — run time for simple parallelized actions
- `rt_per_kf` — run time per locomotion keyframe when interleaving movement

### What works well in `parallel`
- `morph`
- `turn`
- `scale`
- `fade_out`
- locomotion plans such as `walk_to`, `run_to`, and `trot_to` via interleaving

### Limitations
In an ordinary `parallel` block every step shares the block's one run time, and `say` is **not** parallel-safe: its handler ignores `collect_anims` and always fires sequentially via its own `self.play()` call.

To overlap dialogue with movement, or to start steps on different frames, make the block a **timed** one (section 9) by giving its steps `at` and `frames`. A block without those keys plays exactly as described here.

Other multi-step choreography (`wave`, `sit_down`, `stand_up`, `carry`) degrades to sequential execution in an ordinary block and is not allowed in a timed one.

## 9. The timeline: frames, sequences, timed parallel blocks, constraints, choreography routines, stateful props

All of this is opt-in. A screenplay that uses none of the keys and actions below is loaded and played exactly as before.

## The frame clock and `frames`

The timeline counts in frames at **15 per second**, the frame rate of `manim -ql` (which `pam-render` uses by default). Manim's 30 and 60 fps qualities are whole multiples of it, so a length in frames is exact at every quality.

`"frames": n` gives a step's length in frames. Use it in place of the action's seconds key (`rt`, `t`, `hold`), not with it; if both are present the frames win and `pam-validate` warns.

```json
{"action": "morph", "who": "abraham", "pose": "pull_lean", "frames": 12}
{"action": "wait", "frames": 9, "beat": "comic_hold"}
```

At the top level and in a `sequence`, `frames` is understood by `wait`, `morph`, `turn`, `scale`, `slip_on_back`, `fade_out`, `say`, the choreography routines (`pull_immovable`, `cork_pop_up`, `mismatched_hug`), `prop_transition` (also one that writes on a scroll or reshapes a rope), and a timed `parallel` block. More actions accept it inside a timed block (below).

## `sequence`

A named run of steps on the frame clock.

### Keys
- `id` — name used in the console report and the trace
- `do` — the steps, played in order exactly as at the top level

### Notes
- the console reports the frames the sequence ran on, and any step that did not take the frames it asked for
- `"beat": "name"` on a step names the frame it starts on; beats are reported and written to the trace
- constraints started in a sequence end with it

## Timed `parallel` blocks

A `parallel` block is timed when the block has `frames`, or when any step in its `do` list has `at`, `frames`, `frames_in` or `frames_out`, is a `sequence`, is a camera marker, is a choreography routine, or is a `prop_transition`. Each step then starts on its own frame and lasts its own number of frames.

```json
{"action": "parallel", "id": "s02_overlap", "frames": 84, "do": [
  {"action": "sequence", "id": "abraham_arrives", "do": [
    {"action": "walk_to", "who": "abraham", "x": 0.8, "frames": 30, "beat": "walk_in"},
    {"action": "morph", "who": "abraham", "pose": "look_up_point", "frames": 6}
  ]},
  {"action": "turn", "who": "isaac", "pose": "standing_side", "at": 6, "frames": 9},
  {"action": "say", "who": "isaac", "text": "You walked all this way?", "at": 12, "frames": 30},
  {"_subscene_marker": "s02_overlap_medium", "at": 30,
   "_shot_meta": {"framing": "medium", "subject": "isaac", "move": "static"}},
  {"action": "wait", "at": 75, "frames": 9, "beat": "comic_hold"}
]}
```

### Keys on the block
- `do` — the steps
- `id` — name used in the console report and the trace
- `frames` — the block lasts exactly this long; what is left after its last step is stillness. Without it the block ends when its last step ends
- `rt` — default length, in seconds, of a step that gives none (default 0.4, which is 6 frames)
- `rt_per_kf` — default seconds per keyframe of a walk, run or trot (default 0.20, which is 3 frames)

### Keys on a step
- `at` — the frame, counted from the start of the block, on which the step starts (default 0). Only for steps written directly in the block
- `frames` — the step's length. Without it the step's seconds key is used, then the block's `rt`
- `beat` — names the frame the step starts on

### What a step may be

| Step | What it does in a timed block |
|---|---|
| `morph`, `turn`, `scale`, `slip_on_back`, `fade_out` | one move over the step's frames |
| `walk_to`, `run_to`, `trot_to` | with `frames`, the whole move takes exactly that long; without, each keyframe takes 3 frames and the length depends on the distance |
| `say` | the bubble fades in, holds, and fades out as three timed pieces. `frames` is the whole line, `frames_in` and `frames_out` the fades (defaults 6 and 5). With `persist` there is no fade-out. Human, alien and dog characters |
| `wait` | stillness; with a `sound` key and no length, a sound effect on an exact frame |
| `constrain`, `release` | the contact starts or ends on that frame |
| `prop_transition` | a prop changes state on that frame; with `frames`, its move to a new attachment, a number on its display that climbs, text written on a scroll or crossed out, or a rope changing shape (wound round, pulled tight, snapping), takes that long (see "Stateful props" below) |
| `pull_immovable`, `cork_pop_up`, `mismatched_hug` | a choreography routine (below): its phases follow one another, each a set number of frames; `frames` is the whole routine |
| `react` with `fragment` | a mannerism (`pam/tics.py`): each keyframe of its cycle, then the return to the pose it started from, shared over `frames` (below) |
| `sound_cue` | a word such as THUD! that fades in, holds and fades out on exact frames (section 8) |
| `_subscene_marker` | a camera cut on that frame; with `frames`, or an animated `move` (`push`, `pull`, `pan-follow`, `drift`, `zoom`), the camera travels for that long. A shot with `"fit": "bounds"` (section 11) is framed from its subject, and from where the block's steps take the subject before the block's next cut |
| `sequence` | a track: its steps follow one another, the first starting on the sequence's `at`. Use one per actor |

### Limitations
- Actions that play several animations of their own cannot be steps of a timed block: `wave`, `nod`, `shake_head`, `shrug`, `carry`, `sit_down`, `stand_up`, `rotate`, `prop_say`, and the camera moves `pan-up`, `pan-down`, `descend`, `push-into`. The player skips such a step with a message; `pam-validate` reports it as an error. Put it before or after the block.
- A `parallel` block cannot be a step of a timed block, and a `sequence` cannot be nested in a `sequence` there.
- Two `prop_transition` steps must not change the same prop on the same frames; `pam-validate` reports an error. Put them in one `sequence`.
- Two steps must not move the same figure on the same frames. `morph`, `turn`, `scale`, `slip_on_back`, the walks and runs, the choreography routines and the tics (`react` with `fragment`) each set the figure's whole pose on every frame they run, so two of them at once make the figure jump: the one written later wins while they overlap, and the other takes over again when it ends. The player plays it anyway; `pam-validate` reports an error. Put the two steps in one `sequence`. A contact constraint is the exception: it repositions one limb on purpose and may run under any move.
- A step owns the frames from its first up to, not including, the frame it ends on: a 12-frame step that starts on frame 6 owns frames 6 through 17. A step that starts on frame 18 only touches it and is fine.
- A block's `frames` is a promise. If its steps need more, the player plays them to the end and says how far it ran over, and `pam-validate` reports an error, because every later beat would be that much late.
- A camera cut frames its subject where the subject is drawn on the frame of the cut, also in the middle of a walk, a sliding `morph` or a routine.
- A `fade_out` on a figure that another step is moving holds the figure still where it is while it fades; `pam-validate` warns.
- A bubble shown by `say` stays where it appeared. For a character who talks while walking, use `persist`.
- `depth` on a walk is ignored, as in an ordinary `parallel` block.

### Notes
- Seconds inside a timed block are rounded to the nearest whole frame, halves up, and never to less than one frame (0.3 s is 5 frames). `pam-validate` lists every value that was rounded.
- A step's `sound`, and its character's `sfx`, starts on the frame the step starts.
- Within one frame the order is fixed: steps that end on it are finished first, then steps that start on it are started, both in the order they are written. Two renders of the same screenplay are identical frame for frame.
- The console lists the frames every step ran on.

## `constrain`

Start a contact constraint: a hand or foot held on another figure's joint, on a prop, or on a point of the stage, or a figure held where it stands. See `pam/constraints.py` for the solver's rules.

```json
{"action": "constrain", "id": "grip", "type": "joint_to_joint",
 "who": "abraham", "joint": "rwrist", "target": "isaac", "target_joint": "lwrist", "blend": 6}
{"action": "constrain", "id": "on_knife", "type": "joint_to_prop",
 "who": "isaac", "joint": "rwrist", "prop": "knife", "point": "top"}
{"action": "constrain", "id": "on_rock", "type": "joint_to_point",
 "who": "abraham", "joint": "lwrist", "point": [-2.0, -1.4]}
{"action": "constrain", "id": "isaac_root", "type": "root_lock", "who": "isaac"}
```

### Keys
- `id` — name used by `release` and in reports (required)
- `type` — `joint_to_joint`, `joint_to_prop`, `joint_to_point` or `root_lock`
- `who` — the figure that yields
- `joint` — the wrist or ankle that is held on the target (`root_lock`: the joint that stays put, default `lankle`)
- `target`, `target_joint` — `joint_to_joint`: the other figure and the joint the hand stays on
- `prop` — `joint_to_prop`: the prop or scene object the hand stays on
- `point` — `joint_to_point`: the stage position `[x, y]`. `joint_to_prop`: where on the prop, `center` (default), `top`, `bottom`, `left`, `right`, or `[dx, dy]` from its center
- `blend` — frames the hand takes to reach the target (default 0: at once)
- `frames` — release by itself after this many frames
- `bend` — `keep` (default), `up` or `down`: which way the elbow or knee bends

### The four constraint types

| Type | What it does |
|---|---|
| `joint_to_joint` | keeps `who`'s hand or foot on `target`'s `target_joint`, wherever that joint goes |
| `joint_to_prop` | keeps it on a prop. The prop is measured as it is drawn on every frame, so the hand follows a prop that is moved, carried or handed over |
| `joint_to_point` | keeps it on a fixed point of the stage while the rest of the body moves |
| `root_lock` | keeps a figure where it stands, whatever else tries to move it |

### Notes
- the three `joint_to_...` types solve the elbow or knee on every frame with the same two-bone solver; bone lengths do not change and the joint never flips side
- which way it bends: a limb that is bent when the constraint starts keeps the way it is bent. A limb that is straight then (within 2% of its length) bends to the side of the line to the target that its elbow or knee is on. `bend` overrides both
- if the target is out of reach the limb straightens toward it and stops short; the shortfall is reported and is not an error
- the figure named by `who` yields; the other figure, the prop, or the point does not. Root locks are applied first on every frame, then the other constraints in the order they were declared, so a hand may hold a wrist that is itself held on a point if the point's constraint comes first
- a constraint with a bad joint, prop or point is skipped with a message; it never stops the render

## `release`

End a constraint on the current frame.

### Keys
- `id` — the constraint to end

## Choreography routines

A routine is an action that works out its own blocking from the figures as they stand: their scale, their limb lengths, where their hands and feet are. Change a character's size or position and the same step still plays. The routines are in `pam/choreography.py`.

```json
{"action": "pull_immovable", "who": "abraham", "target": "isaac", "frames": 30}
{"action": "slip_on_back", "who": "abraham", "frames": 4}
{"action": "cork_pop_up", "who": "isaac", "target": "abraham"}
{"action": "mismatched_hug", "who": "abraham", "target": "isaac", "frames_squeeze": 18}
{"action": "catch_by_collar", "who": "isaac", "target": "abraham", "release": false}
{"action": "tie_wrist_loop", "who": "abraham", "target": "isaac", "cycles": 3}
```

A routine is a step like any other: at the top level, in a `sequence`, or in a timed `parallel` block (with `at`), where it overlaps dialogue, camera cuts and other actors.

### Phases

The two-figure routines are made of phases that follow one another, each a whole number of frames.

| Routine | Phases and their default lengths in frames |
|---|---|
| `pull_immovable` | `reach` 6, `pull` 12, `strain` 12 |
| `cork_pop_up` | `offer` 6, `accept` 6, `pop` 3, `land` 2, `hold` 9 |
| `mismatched_hug` | `approach` 6, `reach` 6, `squeeze` 12, `release` 6 |
| `catch_by_collar` *(Stage 6b)* | `slip` 3, `catch` 3, `dangle` 18, `set_down` 9 |
| `tie_wrist_loop` *(Stage 6b)* | `approach` 6, `wind` 18, `knot` 9, `yank` 3, `let_go` 6 |

- `"frames_<phase>": n` sets one phase, for example `"frames_strain": 20`. `0` skips the phase
- `"frames": n` sets the whole routine. The phases that were not set one by one share what is left, in proportion to their defaults, at least one frame each
- each phase starts a beat named `<id>.<phase>` (`pull.strain`), reported on the console and written to the trace
- a phase given 0 frames is skipped, and its moves are not made. The two Stage 6b routines start each phase from the figures as they are, so a step that gives frames to only some of their phases plays just those (see below)

### Keys common to the routines
- `who`, `target` — the two figures (required; human figures)
- `id` — name for reports, beats and the routine's constraints (default `<action>_<who>`)
- `frames`, `frames_<phase>` — see above
- `at`, `beat` — as for any step of a timed block

## `pull_immovable`

`who` turns to face `target`, takes hold (`reach`), leans back until his arm is taut (`pull`), and heaves (`strain`). `target` is root-locked and does not move. When the routine ends the grip and the lock are released; follow it with `slip_on_back`.

### Keys
- `joint` — the hand that grips (default: the one the lean reaches with)
- `target_joint` — what it grips (default: the wrist of `target` nearest `who`; if that is out of reach from where `who` can stand, the nearest knee, then ankle)
- `cycles` — number of heaves in `strain` (default 2; 0 holds still)
- `lock` — `false`: do not root-lock `target`
- `release` — `false`: keep the grip (constraint `<id>.grip`) and the lock (`<id>.root`) after the routine; end them with `release`

### What it measures
The arm of `who` and the position of the gripped joint. The stance is worked out so that at the full lean the shoulder is one arm's length, less 4%, from that joint; `who` shuffles to it during `reach`.

## `slip_on_back`

The feet shoot out and the figure lands flat on its back, on the ground its feet were standing on.

### Keys
- `who` — the figure
- `frames` — length of the fall (default 4), or `rt` in seconds
- `direction` — `left` or `right`: where the head ends up (default: the side the head is already leaning to)
- `slide` — how far the feet shoot forward, as a fraction of the figure's leg length (default 0.35)

## `cork_pop_up`

`who` bends and holds a hand out to where `target`, who is lying down, can reach it (`offer`). `target` takes it (`accept`). `who` straightens and `target` comes up onto his feet and off the ground (`pop`), drops back onto it (`land`), and both stand still (`hold`).

### Keys
- `joint` — the hand `who` offers (default: the one toward `target`)
- `target_joint` — the hand `target` takes it with (default: the one nearest the offered hand)
- `hop` — how high `target` leaves the ground, as a fraction of his leg length (default 0.25). It is raised by itself when `who` is so tall that `target` could not otherwise keep hold of the hand
- `pose` — the pose `target` lands in (default `standing_side`, turned to face `who`)

### What it measures
Both figures' arms and shoulders. The hand is offered at a point 80% of `target`'s arm length from his shoulder, toward `who`'s shoulder. `who` bends at the hips, and then at the knees, only as far as his own arm needs to get there. `target` lands on his feet where his feet were, moved only as far as needed to stay clear of `who` and keep hold of the hand.

## `mismatched_hug`

`who` steps in against `target` (`approach`), throws both arms around him (`reach`), squeezes (`squeeze`), and lets go (`release`).

### Keys
- `cycles` — number of squeezes (default 2; 0 holds still)
- `release` — `false`: stay in the hug. There is then no `release` phase, and the arms stay (constraints `<id>.upper` and `<id>.lower`) until a `release` step or the end of the enclosing `sequence`

### What it measures
How wide `target`'s body is at the height of `who`'s shoulders: the torso outline between shoulders and hips, or the legs below them. `who` stands against the near side and each hand goes to the far side. If the arms are too short they straighten and stop short, and that is the joke. The console reports the width, the arm length and the shortfall:

```text
PAMPlayer: mismatched_hug 'hug' (abraham -> isaac) ran frames 97-127; arm 0.8648, width 0.9964, ..., reaches_around False, shortfall 0.3278
```

## `catch_by_collar` *(Stage 6b)*

`target` (standing on a rock, say) pitches forward toward `who` (`slip`), and `who`'s hand shoots out to meet his collar as he falls; the hand closes on it and he is hoisted up (`catch`); he hangs at arm's length, kicks, and goes limp (`dangle`); `who` lowers him onto his feet on the ground `who` stands on and lets go (`set_down`). The hand is held on the collar by a constraint, `<id>.collar`, from the slip to the set-down. `who` does not take a step, and nothing but his catching arm moves.

```json
{"action": "perform", "id": "s03_catch",
 "phases": {"anticipation": 14, "action": 6, "reaction": 20, "recovery": 10},
 "do": [
   {"phase": "action", "action": "catch_by_collar", "id": "catch",
    "who": "isaac", "target": "abraham",
    "frames_slip": "action", "frames_catch": "action",
    "frames_dangle": "reaction", "release": false},
   {"phase": "recovery", "action": "wait", "until": "recovery", "beat": "dangles"}]}
...  five lines of dialogue, and a shrug and a finger up, while he hangs ...
{"action": "catch_by_collar", "id": "catch", "who": "isaac", "target": "abraham",
 "frames_slip": 0, "frames_catch": 0, "frames_dangle": 0, "frames_set_down": 9}
```

### Keys
- `joint` — the catching hand (default: the one toward `target`)
- `target_joint` — what it takes hold of (default `neck`: the collar); any joint
- `cycles` — kicks in `dangle` (default 2; 0 hangs still)
- `lift` — how far the hanging feet clear the ground at least, as a fraction of `target`'s leg length (default 0.25)
- `pose` — the pose `target` is set down in (default `standing_side`, turned to face `who`)
- `release` — `false`: no `set_down`. He stays hanging, and the hand stays on his collar, through the steps that follow, until a later `catch_by_collar` with the same `id` and only `set_down` (its other phases 0) puts him down, or a `release` of `<id>.collar`. Giving `set_down` 0 frames does the same

### What it measures
`who`'s arm and shoulder, and how far `target`'s collar is above his feet when he hangs (the pose `dangle`). The catch point is in front of the shoulder, at its height, 82% of the arm's length away; it is raised (the arm angled up) if the hanging feet would not otherwise clear the ground by `lift`, and moved out if the hanging body would overlap `who`'s. On the set-down the collar is kept within reach, so `target` lands as near `who` as his arm needs. The console reports the catch height, the hang, the clearance, `feet_clear`, and the shortfall.

## `tie_wrist_loop` *(Stage 6b)*

`who` steps up in front of `target`'s held-out wrists, his hand going up to the coil on his shoulder (`approach`); winds his hands round the wrists in loops that get bigger and wilder, bobbing as he goes (`wind`); fiddles at the knot (`knot`); yanks it tight, jerking back half a step (`yank`); and lets go (`let_go`). The hands are held on moving points (`<id>.rhand`, `<id>.lhand`) measured on `target`'s wrists on every frame, so they follow him. The rope is not part of the routine: give it a `prop_transition` on the same frames. Only `who` moves.

```json
{"action": "perform", "id": "s04_winds_rope",
 "phases": {"anticipation": 6, "action": 24, "reaction": 8, "recovery": 6},
 "do": [
   {"phase": "anticipation", "action": "tie_wrist_loop", "id": "tie",
    "who": "abraham", "target": "isaac",
    "frames_approach": "anticipation", "frames_wind": "action",
    "frames_knot": "reaction", "frames_yank": 0, "frames_let_go": "recovery"},
   {"phase": "action", "action": "prop_transition", "prop": "rope", "to": "tied",
    "until": "action",
    "attached": {"to": "isaac", "joints": ["lwrist", "rwrist"], "mode": "around"}}]}
```

### Keys
- `cycles` — loops in `wind` (default 3)
- `release` — `false`: no `let_go`; the hands stay on the knot. Giving `let_go` 0 frames does the same

Each phase starts from the figures as they are, so the phases can be played apart: a step with only `knot` and `let_go` is fiddling at the knot (`"frames_approach": 0, "frames_wind": 0, "frames_yank": 0`); one with only `knot`, `yank` and `let_go` yanks it tight.

### What it measures
`target`'s wrists, on every frame, and `who`'s arms. `who` stands on the side of the wrists away from `target`'s body, facing them, his shoulders 55% of his arm's length from the knot; the loops' radius is at most 30% of his arm, and less if the knot is far above or below his shoulder. The console reports the arm, the step in, how far the knot is above his shoulder, the radius, the loops, and the hands' shortfall.

### Notes on all routines
- every position is measured on the frame the routine starts, from the figures' joints after body scale, depth rescale and rotation. No routine contains a stage coordinate
- a routine slides `who` to its stance. If that is more than about a leg and a half away the console says so; walk him closer first
- the contacts are ordinary constraints, so the four rules of the solver apply. A routine that cannot reach says so and plays anyway
- a routine sets the whole pose of the figures it moves (`who`; for `cork_pop_up` and `catch_by_collar` also `target`), so no other step may move them on the same frames: `pam-validate` reports an error. A hold that a routine leaves in force (`release: false`) is a constraint, and other steps may move the figures under it
- `abe-isaac_scene2-gags.json` plays all four routines, two of them inside timed blocks

## Acting in four phases: `perform` (Milestone 6)

An action that matters is acted in four phases: **anticipation** (the
wind-up: the hand goes to the satchel, Isaac offers his hand),
**action** (the thing itself), **reaction** (the result lands: the
fall, the image held), and **recovery** (settling back). A `perform`
holds the length of each phase in one table and places its steps by
phase, so that a phase is retimed by changing one number, without
touching the steps.

```json
{"action": "perform", "id": "s02_cork",
 "phases": {"anticipation": 15, "action": 3, "reaction": 11},
 "do": [
   {"phase": "anticipation", "action": "cork_pop_up", "id": "cork",
    "who": "isaac", "target": "abraham",
    "frames_offer": "anticipation", "frames_accept": "anticipation",
    "frames_pop": "action",
    "frames_land": "reaction", "frames_hold": "reaction"}
 ]}
```

### Keys
- `id` — names the block and its beats
- `phases` — `{"anticipation", "action", "reaction", "recovery"}`: the frames of each; a phase not given has none. They follow one another in that order, and the block lasts exactly their sum
- `do` — the steps

### Keys on a step of a `perform`
- `phase` — the phase the step starts in. Without it the step is placed as in any timed block
- `at` — frames after the start of the step's phase
- `until` — the name of a phase: the step lasts until that phase ends (its own or a later one), in place of `frames`
- on a routine, `"frames_<its phase>": "<acting phase>"` — the acting phase's frames (from where the routine starts, when it starts inside it) are shared by every routine phase that names it, in proportion to their default lengths. A number still sets one phase

### Notes
- A `perform` is a timed `parallel` block: it is expanded into one when the screenplay is loaded (`pam/timeline.py`, `expand_perform`). Everything a timed block may hold may be a step of it, with the same rules; the console report and the trace show the block
- each phase that has frames is a beat, `<id>.<phase>`, as long as the phase (a `wait` added at the end of the block's steps)
- a step that starts after the end of its `until` phase gets 0 frames, and `pam-validate` reports it; so does an unknown phase name, a phase that is not a whole number of frames, and a step with both `frames` and `until`
- a `perform` may stand at the top level or in a `sequence`, not in a `parallel` block
- not every line needs one. A line of dialogue with no gesture is a plain `say`

## Mannerisms on the frame clock: `react` with `fragment` (Milestone 6)

`react` plays the character's react-triggered tics (`tic_profile`), as
before. With `fragment` it plays that one mannerism, whatever the
profile says, on the frame clock: each keyframe of the fragment's cycle
is a change from the pose the figure has when the tic starts, and the
last piece returns it to that pose.

```json
{"action": "react", "who": "abraham", "fragment": "count_tap_r", "frames": 5, "at": 2}
{"action": "react", "who": "abraham", "fragment": "scribble_r", "cycles": 3, "frames": 30}
```

### Keys
- `who`
- `fragment` — a name in `pam.tics.TIC_FRAGMENTS`
- `frames` — the whole tic, shared evenly over its keyframes and the return; without it, two frames a keyframe
- `cycles` — how many times the cycle repeats (default 1)
- `at`, `beat`, `sound` — as on any step of a timed block

### Fragments added in Milestone 6
| Fragment | What it does |
|---|---|
| `count_tap_r` | a finger of the right hand ticks off an item on the raised left hand (from the pose `count_hand`) |
| `nod` | the head dips and comes back |
| `head_shake` | the head turns side to side |
| `scribble_r` | the writing hand moves along a line in little loops |
| `flick_r` | one stroke of the writing hand |
| `finger_wag_r` | a raised finger wagged |
| `shrug` | shoulders up, hands out |
| `startle` | the whole body jumps a little |
| `chest_pat_r` | a hand pats the chest twice |

### Fragments added in Stage 6b
| Fragment | What it does |
|---|---|
| `pant` | the shoulders, head and hands heave up and drop: out of breath |
| `leg_kick` | the legs kick, one forward and one back, then the other way (a man hanging in the air) |
| `tremble` | both hands shake, a little and quickly, so that a prop held in either one trembles (repeat with `cycles`) |
| `bar_bounce` | the shoulders hitch up and drop, and what rides on them (the barbell) bounces |
| `wrist_tug` | tied wrists tugged apart and let go: testing the knot |

`pant`, `bar_bounce` and `wrist_tug` move joints only up and down, so they read the same on a figure facing either way.

A tic sets the figure's whole pose, so it may not overlap another move
of the same figure (`pam-validate` reports an error).

## Stateful props

A stateful prop has a state (`intact`, `broken`, ...), may be made of parts, may have a display, may bear text, may change shape (a rope), and is kept on an attachment: a character's joint, another prop, or a place on the stage. One action changes all of it, `prop_transition`. The module is `pam/prop_states.py`; its first page is the full reference.

A prop is stateful when its item says so (any of the keys `state`, `attached`, `parts`, `display`, `states`), when it is a composite type (`knife`, `composite_prop`, `rope`) or a text-bearing one (`scroll`), when a `prop_transition` names it, or when the continuity ledger carries it. Every other prop is built and played as before.

```json
{"action": "props", "items": {
  "bowl":  {"type": "bowl", "x": -0.55},
  "knife": {"type": "knife",
            "attached": {"to": "abraham", "joint": "lhip", "hidden": true}},
  "phone": {"type": "phone",
            "attached": {"to": "isaac", "joint": "rwrist", "by": "bottom"}}}}
```

### Keys of a stateful prop item
- `state` — the state it starts in (default: the machine's first state)
- `attached` — where it starts (an attachment, below). Not the older `attach` key, which names a point on a `parent` and keeps its meaning
- `display` — starting values of its display fields
- `text` — a `scroll`: what it says before any revision, a list of lines
- `parts` — `{part: {"attached": {...}}}`: where the parts of a composite prop start when they are apart
- `states`, `initial_state`, `transitions` — a machine of the item's own (see `composite_prop`)

### Machines

| Prop type | States | Notes |
|---|---|---|
| `knife` | `intact`, `broken`, `blade_carried`, `blade_embedded` | composite: parts `handle` and `blade`. Nothing leads back to `intact`. `blade_carried` needs the blade's attachment mode `in` or `held`; `blade_embedded` needs `embedded` |
| `phone`, `cellphone`, `smartphone` | `standby`, `recording`, `live` | display fields `viewers` (a whole number) and `comment` (text or null) |
| `scroll` | `rolled`, `unrolled`, `edited`, `trailing` | bears text, changed by `text` steps only while it is `edited`. From `rolled`: `unrolled` or `trailing`; it is unrolled before it is written on. From any open state it may be rolled up or let trail |
| `rope` | `loose`, `tied`, `tightened`, `snapped` | deformable and composite: pieces `piece_a` and `piece_b`. `tied` and `tightened` need the rope's attachment mode `around`; `loose` needs any other. `loose` to `tied` to `tightened`, `tightened` back to `tied`, either back to `loose`, and any of them to `snapped`. Nothing follows `snapped` |
| `pocket_door`, `elevator` | `closed`, `open` | the state is the prop's `is_open`; entering it calls `open_doors` / `close_doors` |
| `avatar_pod`, `pod` | `closed`, `open` | `is_open`; `open_lid` / `close_lid` |
| `dodecahedron` (the Governor) | `gold`, `amber`, `dark` | the Governor's own state; `set_state` |

The last three rows are the props that already had a state. `elevator_open`, `elevator_close`, `open_lid`, `close_lid` and `prop_color` work as before and go through the same machine, so `{"action": "prop_transition", "prop": "lift", "to": "open"}` and `{"action": "elevator_open", "who": "lift"}` do the same thing.

## `prop_transition`

Put a prop in a state, move it or its parts to new attachments, change what its display shows, or any of these at once.

```json
{"action": "prop_transition", "prop": "knife",
 "attached": {"to": "abraham", "joint": "rwrist", "by": "blade", "angle": 180}}

{"action": "prop_transition", "prop": "knife", "to": "broken", "frames": 6,
 "parts": {"handle": {"attached": {"to": "isaac", "joint": "lwrist"}},
           "blade":  {"attached": {"to": "bowl", "point": "top", "mode": "in"},
                      "rate": "rush_into"}}}

{"action": "prop_transition", "prop": "phone", "to": "live", "display": {"viewers": 3}}
{"action": "prop_transition", "prop": "phone", "display": {"viewers": 240}, "frames": 30}

{"action": "prop_transition", "prop": "scroll", "to": "edited", "frames": 24,
 "text": {"replace": "THE KNIFE?", "with": "HIS SON."}}
```

### Keys
- `prop` — the prop, or one part of a composite prop written `prop.part` (`knife.blade`)
- `to` — the state to enter. Optional: a step may only move the prop or only change its display
- `attached` — where the prop (or the named part) goes
- `parts` — composite props: `{part: {"attached": {...}, "rate": ...}}`
- `display` — new values of display fields
- `text` — a `scroll`: changes to what it says, one op or a list (see "The `scroll`" below)
- `frames` — how long the move, a number that climbs, writing or crossing out, and a rope's change of shape take (default 0: at once). The state changes on the first frame
- `rate` — easing of the move: `smooth` (default), `linear`, `rush_into` (a fall), `rush_from`
- `at`, `beat`, `sound` — as for any step of a timed block
- `rt` or `run_time` — doors, lids and the Governor only, outside a timed block: the length of the prop's own animation in seconds (default 0.6)

### An attachment
- `to` — a character, a prop or scene object, or `null` (at rest on the stage)
- `joint` — on a character: the joint the prop stays on (default `rwrist`)
- `joints` — on a character, instead of `joint`: several joints. A rope with mode `around` goes round all of them (`["lwrist", "rwrist"]`); any other prop stays on their middle (held between two hands)
- `point` — on a prop: where, as for `joint_to_prop`: `center` (default), `top`, `bottom`, `left`, `right`, or `[dx, dy]` from its center
- `by` — which place of the moved prop sits there: one of the same names, a part of a composite prop (`"by": "blade"`), or a named point of the prop (`"by": "grip"` on a scroll). Default: the prop's anchor if it has one (a scroll's grip; `center` there means the grip too), else `center`
- `offset` — `[dx, dy]` added to the target
- `x`, `y` — with `"to": null`: where on the stage (default: where it is)
- `angle` — the prop's orientation in degrees, counterclockwise (default: as it is). The knife's blade points to +x at 0
- `mode` — what kind of attachment: `held` (default on a character), `on` (default on a prop), `in`, `embedded`, `free` (default at rest), `around` (wound round the joints or the prop: a rope; not at rest)
- `hidden` — `true`: out of sight (in a satchel, in a pocket). The prop is not drawn, and is still there

### Notes
- an attachment is kept on every frame: the prop goes where the hand or the parent prop goes, also when the hand is held by a contact constraint
- a prop attached to a character who has not faded in yet, or to a prop that is not on stage, is not drawn until they are
- while a composite prop is in one piece its parts move with it, and a part cannot be attached by itself; once the pieces are apart the whole cannot be moved, only its parts. When it comes apart, a part the step does not mention stays where the whole was
- the state changes only along the machine's transitions; a step that asks for anything else is skipped with a message, and `pam-validate` reports it as an error
- with `frames`, a `prop_transition` runs on the frame clock wherever it stands: at the top level, in a `sequence`, or as a step of a timed `parallel` block
- a number on a display climbs evenly over the step's frames, one value per frame; anything else on the display (a comment) is new from the first frame
- text on a scroll is written evenly over the step's frames, letter by letter; a crossed-out phrase gets its line drawn from left to right first (see "The `scroll`")
- in a timed block a door, lid or Governor transition needs `frames`
- `reparent_prop`, `move_prop` and the hand-off actions (`pick_up`, `grab`, `hand_to`, `put_down`, `place_on`, `stick_to`, ...) keep their behavior. On a prop that is being kept on an attachment they let go of it first, and the new place is entered in the books
- the console reports every change with its frame:

```text
PAMPlayer: prop 'knife' intact -> broken; knife.handle held by isaac (lwrist); knife.blade in bowl on frame 66, over 6 frames.
```

## The `knife`

A composite prop: `knife.handle` and `knife.blade` are two props from the start, registered under those names, so a camera subject, a `joint_to_prop` constraint or an attachment can name either. The knife itself draws nothing of its own, so nothing is ever drawn twice, and the two parts are the same two props before and after it breaks. `"type": "knife_handle"` and `"type": "knife_blade"` can also be declared by themselves.

`composite_prop` builds a composite from the parts its item lists, with a machine of its own:

```json
"sword": {"type": "composite_prop", "initial_state": "whole",
          "parts": {"hilt": {"type": "knife_handle", "offset": [-0.13, 0]},
                    "edge": {"type": "knife_blade", "offset": [0.08, 0]}},
          "states": {"whole": {"connected": true}, "snapped": {"connected": false}}}
```

## The `phone`

A cellphone's screen shows its state: dim in `standby`, a red LIVE button in `recording`, and in `live` a LIVE badge, the viewer count and a comment. The display and the phone's place are independent: a step may change one and leave the other.

New plain props that the Abraham and Isaac scenes use, for other props to go into, rest on or stick in: `satchel`, `bowl`, `rock`, `altar` (three stones; `[-0.30, 0.18]` from its center is the gap between the first two).

Milestone 6 adds two more, both standing on `y`: `barbell` (two boulders and a log; `width`, `height`; attachment points `left` and `right` where the hands grip the log) and `magazine` (`width`, `height`; `cover`, the words on its cover, one to a line and as large as fits; `stack`, a pile of that many lying flat). Held between two hands (`"joints": ["lwrist", "rwrist"]`), a barbell stays on their middle.

The barbell is a composite prop, like the knife: three parts, `<name>.left` and `<name>.right` (the boulders, type `barbell_boulder`) and `<name>.log` (type `barbell_log`), with two states. While it is `assembled` (the first state) the parts move as one. In `altar` they are apart, each attached on its own; nothing leads back. In Scene 4 of Abraham and Isaac, Isaac builds the altar from it:

```json
{"action": "prop_transition", "prop": "barbell", "to": "altar", "frames": 15,
 "parts": {"left":  {"attached": {"to": null, "x": 0.98, "y": -2.6, "by": "bottom", "angle": 9}},
           "right": {"attached": {"to": null, "x": 2.22, "y": -2.6, "by": "bottom"}},
           "log":   {"attached": {"to": null, "x": 1.6, "y": -1.85, "by": "bottom"}}}}
```

After that a part moves by itself (`"prop": "barbell.left"`), and other props can attach to it: the blade sticks in `barbell.log` in Scene 5.

## The `scroll`

A text-bearing prop. Two dimensions of its state change independently: its **state**, how it is open (`rolled`, `unrolled`, `edited`: open and being written on, `trailing`: unrolled further and streaming out from its grip like a banner), and its **text**, every line with every revision. Rolling, unrolling and trailing never change the text, and writing never changes the state or where the scroll is. One step may do several of these at once.

```json
{"action": "props", "items": {
  "scroll": {"type": "scroll", "text": ["GENESIS / B'RESHIT"],
             "attached": {"to": "abraham", "joint": "lwrist"}}}}
{"action": "prop_transition", "prop": "scroll", "to": "unrolled", "frames": 6}
{"action": "prop_transition", "prop": "scroll", "to": "edited", "frames": 30,
 "text": {"write": "AND ABRAHAM RAISED THE KNIFE."}}
{"action": "prop_transition", "prop": "scroll", "frames": 6,
 "text": {"replace": ".", "with": "?", "line": 2}}
{"action": "prop_transition", "prop": "scroll", "frames": 24,
 "text": {"replace": "THE KNIFE?", "with": "HIS SON."}}
{"action": "prop_transition", "prop": "scroll", "to": "trailing", "frames": 6}
```

### Text ops

A `text` key holds one op or a list of them. The ops of one step are applied in order, each to what the one before left, and each is one revision.

| Op | What it does |
|---|---|
| `{"write": "..."}` | writes a new last line |
| `{"write": "...", "line": n}` | writes at the end of line `n` |
| `{"cross_out": "..."}` | draws a line through the phrase; it stays on the page and no longer counts as what the scroll says |
| `{"replace": "...", "with": "..."}` | crosses out the phrase and writes the new text right after it |

- `line` — counts from 1; `-1` is the last line. On `cross_out` and `replace` it says where to look
- `occurrence` — which match, from 1, when the phrase is said more than once
- a phrase is looked for in what the line says, leaving out crossed-out text: after `.` is replaced by `?`, the line says `THE KNIFE?`
- a phrase that is not there, or is there more than once with no `line` or `occurrence`, is an error (`text-not-found`, `text-ambiguous`)
- text is written only while the scroll is `edited` (`not-writable` otherwise). `"to": "edited"` in the same step puts it there first
- a word written right after crossed-out text is set one column apart from it

### On the frame clock

With `frames`, each letter written is one stroke, and each three letters crossed out are one stroke (at least two for a phrase); the strokes are spread evenly over the frames. Crossing out comes before the writing that replaces it. Without `frames` the change is there at once.

### Where it is

The scroll is drawn in its own frame from its **grip**, the middle of its near roller, and is kept on an attachment by the grip: rolled, open or trailing, the grip stays in the hand that holds it. `angle` turns it about the grip; a trailing scroll at angle 0 streams out to the right of the hand. The open sheet shows the last seven lines, set in a monospaced font in fixed columns; a line too long for the sheet is set smaller.

### In the ledger

The scroll's state, text and revisions go into the ledger. Each revision records its number, the op, the line it was made on, and the scene it was made in:

```json
"text": {"lines": [[{"text": "GENESIS / B'RESHIT", "rev": 0}],
                   [{"text": "AND ABRAHAM RAISED ", "rev": 1},
                    {"text": "THE KNIFE", "rev": 1, "struck": 3},
                    {"text": ".", "rev": 1, "struck": 2},
                    {"text": "?", "rev": 2, "struck": 3},
                    {"text": "HIS SON.", "rev": 3}]],
         "revisions": [{"rev": 1, "write": "AND ABRAHAM RAISED THE KNIFE.", "line": 2, "scene": "scene1"},
                       {"rev": 2, "replace": ".", "with": "?", "line": 2, "scene": "scene1"},
                       {"rev": 3, "replace": "THE KNIFE?", "with": "HIS SON.", "line": 2, "scene": "scene6"}]}
```

A `quill` is a plain prop, to write with.

## The `rope`

A deformable prop: a curve whose shape is worked out on every frame from what it is attached to. It is also a composite prop of two pieces, `rope.piece_a` and `rope.piece_b`, joined end to end, which are two props from the start (like the knife's handle and blade): after the rope snaps each piece keeps its own identity, and nothing is ever drawn twice.

```json
{"action": "props", "items": {
  "rope": {"type": "rope", "attrs": {"scale": 1.4},
           "attached": {"to": "abraham", "joint": "rshoulder", "mode": "on"}}}}
{"action": "prop_transition", "prop": "rope", "to": "tied", "frames": 18,
 "attached": {"to": "isaac", "joints": ["lwrist", "rwrist"], "mode": "around"}}
{"action": "prop_transition", "prop": "rope", "to": "tightened", "frames": 3}
{"action": "prop_transition", "prop": "rope", "to": "snapped", "frames": 12,
 "rate": "rush_into",
 "parts": {"piece_a": {"attached": {"to": null, "x": 0.25, "y": -2.6}},
           "piece_b": {"attached": {"to": null, "x": 2.95, "y": -2.6}}}}
```

### Its shape in each state

| State | Attached | Shape |
|---|---|---|
| `loose` | to a character (`held`, `on`) | a coil hanging from the joint: over a shoulder, from a hand |
| `loose` | to a prop (`on`, `in`) | a coil lying on the prop's point |
| `loose` | at rest | a coil lying on the ground, its bottom at `x`, `y` |
| `tied` | `around` a character's `joints`, or a prop | wound three times round all of them, clear of the joints as they are drawn, with a knot on top and its two ends sticking out of the knot |
| `tightened` | the same | the same, pulled tight: closer round them, and a smaller knot |
| `snapped` | each piece: at rest, or on or in a prop | lying where it fell: along the ground, its lowest point on `y` and its middle on `x` (`angle` turns it) |
| `snapped` | each piece: held by a character | hanging from the joint |
| `snapped` | each piece: `around` | its half of the loop |

- tied, the rope follows the joints it is tied to on every frame: when the wrists move, the loop moves and stretches with them
- the rope breaks in the middle of its length, which is under the loop, between the wrists
- with `frames`, a step that moves the rope or changes its state turns the shape it had into the new one over those frames: the coil leaves the shoulder and winds round the wrists, the knot is pulled tight. The rope keeps its size on the way (it does not shrink to a knot halfway). On its way round joints it was not round before, it aims at a loop drawn in toward their middle, which opens out to the joints as it arrives, so a rope tied round two hands coming together flies into the hands rather than stretching between them. To have Abraham seem to tie it on as Isaac holds out his wrists, give Isaac's `morph` and the rope's step the same `at` and `frames` in a timed block
- a snap with `frames` throws each broken end back along its piece, away from the break, for the first half of the step; the pieces then fall (use `"rate": "rush_into"`) and lie where their attachments put them
- a piece the snap does not mention stays where the rope was
- at rest with no `x` or `y`, a piece or a coil stays where it is (in the air, if that is where it was): give both
- `attrs.scale` makes a rope that many times the usual size and thickness (coil, loop, knot, the length of a piece at rest). Isaac's wrists are big, and the loop fits round them by itself

### In the ledger

The rope's state, its pieces and their attachments go into the ledger, like the knife's. A rope tied round two wrists is recorded with both joints:

```json
"rope": {"type": "rope", "state": "tightened",
         "attached": {"to": "isaac", "kind": "character",
                      "joints": ["lwrist", "rwrist"], "mode": "around"},
         "parts": {"piece_a": {"type": "rope_piece",
                               "attached": {"to": "rope", "kind": "prop", "mode": "joined"}},
                   "piece_b": {"type": "rope_piece",
                               "attached": {"to": "rope", "kind": "prop", "mode": "joined"}}}}
```

Its shape is not recorded: it follows from the state and the attachments.

## The continuity ledger

The ledger records, for each prop a film carries from scene to scene, its state, its parts, what each is attached to, and what its display shows and its text says, at the end of every scene. It is a `continuity` block in the project's cast-and-props sidecar (`pam_sidecar.json` next to the scenes, or `PAM_SIDECAR`):

```json
[
  {"action": "cast", "characters": {"abraham": {...}, "isaac": {...}}},
  {"action": "continuity",
   "scenes": ["scene1", "scene2", "scene3", "scene4", "scene5", "scene6"],
   "props": {
     "knife": {"type": "knife",
               "attached": {"to": "abraham", "joint": "lhip", "hidden": true}},
     "phone": {"type": "phone",
               "attached": {"to": "isaac", "joint": "rwrist", "hidden": true}}},
   "ledger": {"scene1": {...}, "scene2": {...}}}
]
```

### Keys of the `continuity` block
- `scenes` — the scenes in playing order, by file name without `.json`
- `props` — the props whose state carries over, as they are before the first scene
- `ledger` — written by PAM: one closing entry per scene

### How it works
- a scene listed in `scenes` opens with every one of those props as the scene before left it. They are declared for the scene automatically; a prop the scene declares itself keeps the scene's item
- playing a scene (`pam-render`, `pam_trace.py`) and validating it (`pam-validate`) both write its closing entry, with the same code. The file is rewritten only when an entry changes, and an entry holds no date, so validating a finished film again leaves the file as it is
- a scene may state a carried prop's `state`, `attached`, `parts`, `display` or `text` itself. Where that differs from the ledger it is an override: allowed, and reported by `pam-validate` as a `ledger-override` warning, every time
- `pam-validate` reports an error when a carried prop is attached to something the scene does not have, at the start or at the end of the scene, and when a composite prop has lost a part. A scene with errors does not write its entry, and an entry it wrote earlier is removed
- if the scene before has no entry yet, the nearest earlier one is used and `pam-validate` warns (`ledger-missing`)
- a scene that the block does not list, and any screenplay without such a sidecar, has no ledger

```bash
./pam-validate --project projects/abe-isaac   # every scene, in order, no rendering
./pam-validate scene3.json                    # one scene; writes its entry
./pam-validate scene3.json --no-ledger        # reads the ledger, writes nothing
```

`projects/abe-isaac` holds six scenes that take the knife, the phone, the scroll and the rope through *Abraham and Isaac, Revisited*; `abe-isaac_knife-break.json` is the Scene 2 break by itself, `abe-isaac_scroll-revision.json` the scroll's whole story in one scene, and `abe-isaac_rope-snap.json` the rope's.

### In the trace and in Blender
A scene with stateful props is traced as version 5. `"prop_states"` names each such prop, the prop objects it is made of, its state from each frame on, what its display shows and, for a scroll, its text frame by frame (`"text"`: the letters written so far, and how far each line through struck text is drawn); `"prop_events"` lists every change (`prop_state_changed`) with its frame. A rope's pieces carry their shape, frame by frame, as control points (`"shape"`: sampled pieces, as for constrained limbs). `trace2blender.py` builds each part once, keeps it on its attachment, turns it, hides it, gives the phone its screens, draws the scroll's roll, sheet or ribbon with its text, letter by letter on the same frames, and builds each piece of a rope as a curve object whose points are keyed on every frame the trace has them. A hand held on a prop (`joint_to_prop`) is moved to where Blender puts the prop, and an empty named `contact.<id>` marks the held point.

## Checking a screenplay first

`pam-validate scene.json` checks all of the above without rendering. `pam-validate scene.json --frames` also lists every duration in the screenplay that is not a whole number of frames at 15 fps, with the value it rounds to.

## 11. Camera metadata reference

When camera mode is active, the player consumes `shot_meta` dictionaries.

## `framing`

Supported values in the code:

- `wide`
- `medium`
- `medium-close`
- `close`
- `ots-left`
- `ots-right`
- `oneshot`
- `insert`

These map to internal frame widths and center heights.

## `move`

Supported values in the code:

- `static`
- `push`
- `pull`
- `pan-follow`
- `drift`
- `pan-up`
- `pan-down`
- `descend`
- `push-into`

## `subject`

Usually:
- a character key
- `ensemble`
- a prop name
- a scene-object name
- `governor` / `dodecahedron`

A shot with `fit` (below) may also name a part of a composite prop
(`knife.blade`), and several subjects joined by `+` (`knife+bowl`).

## `fit` and `margin`: a shot framed from its subject (Milestone 5)

```json
{"_subscene_marker": "s05_phone", "_shot_meta": {
  "framing": "insert", "subject": "phone", "move": "static",
  "fit": "bounds", "margin": 0.12}}
```

With `"fit": "bounds"` the camera is not set from the `framing` table and
the subject's horizontal position, but from the subject's bounding box
(`pam/shot_targets.py`).  `framing` and `move` keep their meaning
otherwise (a static cut, or a move that ends on the fitted frame).

### Keys
- `fit` — `"bounds"`, the only value
- `margin` — the fraction of the frame left clear on each side of the
  subject, from 0 to below 0.5 (default 0.12)

### What is framed
- **What is visible of the subject**: every part of it that is on stage
  and drawn. A composite prop is framed from its parts wherever they are
  (the broken knife: the handle in a hand and the blade in the bowl); a
  part that is hidden (in a satchel) is left out.
- **Where the shot takes it**: the steps after the cut, up to the next
  cut, are read before the cut is made. A `prop_transition` among them
  that sends the subject, or a part of it, to a new attachment adds the
  place it is going, so the subject stays in the frame for the whole
  shot. A cut that is a step of a timed block reads the block's steps
  from its frame up to the block's next cut.
- **Only what arrives in the shot**: a step of a timed block counts only
  if it is over by the block's next cut (`at` plus its `frames`, or its
  run time at 15 fps). A move still under way at the cut belongs to the
  next shot. In Scene 2 the handle comes away in one shot and the blade,
  which is still falling at frame 6, lands in the next: an insert on the
  knife (the hands) and an insert on `bowl+knife.blade`.
- **A piece on its way is framed where it lands**: a piece the shot sends
  somewhere is left out of the box where it is at the cut (the blade is
  still in Isaac's hands when the shot of the bowl begins), and framed at
  its attachment, turned to the attachment's `angle`.
- **Where it belongs**: a stateful prop that has not been put on its
  attachment yet is framed where the prop-state books keep it. When that
  is a character who has not faded in yet (Scene 5 opens on the phone in
  Abraham's hand, before he is on stage), the character is built as the
  next `fade_in` will build it (its offset, `x`, `scale`, build and pose)
  to find the hand, and is not added to the scene.
- **A character**: the figure as it is drawn; a character who has not
  faded in yet (a shot that opens a scene) is built as its next
  `fade_in` will build it, and framed there (Milestone 6).
- **Readable text**: when the subject bears text (a scroll's lines, a
  phone's screen) and its smallest cap height would fill less than 3% of
  the frame's height (`shot_targets.TEXT_MIN`), the frame closes in on
  the text instead.
- The frame is never narrower than 0.5 units nor wider than the stage
  (14.2), and it is kept on the stage from left to right.

The console shows each fitted shot, for example
`CAM fit text w=0.54 x=-1.06 y=-1.31, text 5.8% of the height subject=scroll`.
A fitted shot whose subject is not on stage and not in the books is
framed as before, with a message. `pam-validate` checks `fit` and
`margin`, and warns when a fitted shot names no subject or one that is
not a known character or prop.

A shot without `fit` is framed exactly as before. In Fountain+,
`MARGIN=` in a `CAMERA` note asks for it, and `fountain2pam.py
--project` gives every insert `fit` (section 13 of
`fountain2pam-manual.md`).

## 12. Extra camera parameters for special move types

## `pan-up`

### Keys
- `subject` — usually a building or vertical object
- `char_subject` — optional anchor character
- `rt` — tilt-up duration, default 2.5
- `rt_return` — tilt-back duration, default 1.8
- `hold` — hold at top, default 0.8
- `shear` — keystone amount, default 0.18
- `y_squeeze` — optional vertical squeeze factor

---

## `pan-down`

Uses normal framing and subject plus built-in timing.

### Effective key
- `rt` is taken from the internal move table; default 2.5 unless code is changed

---

## `descend`

### Keys
- `from_y` — start camera center y, default 4.0
- `to_y` — end camera center y, default -6.0
- `rt` — total travel time, default 10.0
- `rate` — `smooth`, `linear`, `rush_into`, `ease_in`, `ease_out`
- `bg_color` — optional background color at descent start

---

## `push-into`

### Keys
- `subject` — target prop or scene object
- `rt` — push duration, default 3.0
- `zoom_to_w` — final camera width, default 3.5
- `flash` — whether to use end flash, default true
- `rt_flash_in` — flash fade-in time, default 0.15
- `rt_flash_out` — flash fade-out time, default 0.20

## 13. What `pam_player.py` does not do

It is important to document the negative space too.

`pam_player.py` does **not**:

- define a traditional `argparse` CLI
- convert Fountain directly (`fountain2pam.py` does)
- export Blender scenes (`pam_trace.py` records a trace of the performance, and `trace2blender.py` builds the `.blend` from it)
- validate a screenplay (`pam-validate` does, without rendering)
- define every action implementation inline
- own Manim’s quality flags or output options

Those responsibilities belong to other parts of the PAM toolchain.

## 14. Practical troubleshooting notes

## If nothing renders
Check these first:

1. `PAM_SCRIPT` points to a real JSON file.
2. You ran `manim ... pam_player.py PAMPlayer` with the scene name included.
3. The JSON parses successfully.
4. Your screenplay actually contains visible actions such as `fade_in`, `spawn_prop`, `caption`, or `on_screen_text`.

## If camera motion is wrong
Check:

1. `PAM_CAMERA_MODE` behavior.
2. whether `_subscene_marker` entries exist in the PAM JSON.
3. whether `PAM_PROMPTS` points at the matching prompts file.
4. whether the subject names in `shot_meta` match live character, prop, or scene-object names.

## If a character action is skipped
Common causes:

- `who` does not match a declared cast key
- the character was never faded in
- the action is registry-based and its handler lives in `actions.py`

## If a prop action is skipped
Common causes:

- the prop name does not exist in the registry
- the prop was removed earlier
- the prop type does not support the requested method, for example `open_lid` on a non-pod prop

## 15. Best documentation wording for the CLI section

If you want a compact, precise statement for the final README, use this:

> `pam_player.py` is not a standalone argparse program. You invoke it as the Manim scene `PAMPlayer`, and you configure PAM-specific behavior with environment variables such as `PAM_SCRIPT`, `PAM_CAMERA_MODE`, `PAM_PROMPTS`, and `PAM_SHOW_CLOCK`. For a more flag-oriented interface, use the `pam-render` shell wrapper.

## 16. Minimal operator reference card

```bash
# Default screenplay.json
manim -pql pam_player.py PAMPlayer

# Specific screenplay
PAM_SCRIPT=scene.json manim -pql pam_player.py PAMPlayer

# With timing clock
PAM_SCRIPT=scene.json PAM_SHOW_CLOCK=1 manim -pql pam_player.py PAMPlayer

# With explicit prompts for camera-mode
PAM_CAMERA_MODE=1 PAM_SCRIPT=scene.json PAM_PROMPTS=scene_prompts.json manim -pql pam_player.py PAMPlayer

# High-quality render
PAM_SCRIPT=scene.json manim -pqh pam_player.py PAMPlayer
```

## 17. Bottom line

For users, the most important distinction is:

- **Manim controls rendering options**
- **PAM environment variables control screenplay loading and camera behavior**
- **JSON actions control the actual animation**

That is the correct mental model for `pam_player.py`.
